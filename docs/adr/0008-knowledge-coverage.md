# ADR 0008: keep an explanation as a note, and print the coverage view instead of storing it

Status: accepted. Date 2026-11-20.

## Context

`zw-how` produced one explanation and threw it away (`Artifacts: None. The explanation is the
artifact, and it stays in the conversation.`). The same subsystem then got explained again next
month, at the same cost. Worse, the second read was the only evidence the first was worth paying for.

The notes tree is the obvious home, and it is not free to extend. Two tools write it: this repo's
`zw-write-notes-like-deepseek`, and the upstream `write-notes-like-deepseek` skill installed
directly by people who do not use z-workflow. Four shapes were ruled out by the vendored checkers
rather than by taste:

- A header field (`Scope:`) fails `verify-agent-note-format.ts`, which pins lines 1 to 4 to title,
  blank, `Status:`, blank.
- A seventh class fails `agent-note-tree.ts`, whose class set is closed at six.
- A new `docs/knowledge/` tree is invisible to upstream users, so it rots at a different rate from
  the notes it duplicates.
- An `INDEX.md` fails `agent-note-tree.ts` outright, on the grounds that one shared index is the
  hottest conflict source when several branches edit it.

LiveX Wiki, the reference this work was read from, reaches the same conclusion from the other side:
its compact entry list is generated by a program, and its scenario boundaries cannot be derived from
directories, so a person owns them.

## Decision

An explanation worth paying for twice is kept as an `implemented` Agent Note, in
`implemented/architecture/` or `implemented/feature/`, carrying one free section between
`## Decision` and `## Alternatives considered`:

```markdown
## Scope

payments/refund
payments/settlement/ledger
```

Free sections are legal in both tools, the two class directories are already in upstream's closed set,
and `rejected/` and `archived/` take no new section (archived is sha256-sealed). So a tree written
here still passes upstream's three checkers unchanged. Two triggers, either enough: the user asks for
it, or the subsystem is explained a second time.

The coverage view is printed, never stored. `skills/zw-how/scripts/coverage.mjs` enumerates candidate
units from directory globs, scans `implemented/**` for `## Scope` ids, and prints four blocks:
unclaimed units, claimed ids with their owner from `git log`, notes with no scope, and scope ids that
name no directory. It exits zero whatever it says.

Ownership is derived from git history rather than recorded in a field, so it cannot go stale and
nobody maintains it.

## Consequences

- A note written with the upstream skill directly carries no `## Scope`, so it lands in the
  scope-absent block forever. That block is the adoption curve, not a defect, and it is why the
  report is a hint: a gate here would fail trees written by the tool this repo claims compatibility with.
- No shared index file exists, so the conflict the upstream no-index rule protects against cannot arise,
  at the cost of recomputing the view on each run. That is cheap: a directory walk and a git log per
  claimed note.
- Coverage is per repository, because each notes tree belongs to one repo. A cross-repo view needs a
  host-level index, which is a separate seam and is not built.
- The unclaimed list says `unclaimed`, never `unknown`. A unit with no note may be understood; the
  report can only see claims. Deriving coverage from note titles would produce false coverage, which
  is worse than no view.
- `zw-how` becomes the second place that writes notes, so its body must run the notes gate, and its
  `Done` list no longer claims that no file was written.

## Alternatives considered

- **A `docs/knowledge/` tree with domain/scenario files and generated indexes.** The shape LiveX
  documents, and the one I proposed first. Rejected: it is a seventh document class beside notes,
  ADRs, the glossary, `docs/agents/`, the feature map and specs, and it is invisible to the second
  tool that writes notes. Its whole advantage over notes, an explicit coverage map, is delivered by
  the printed report without a new tree.
- **A `Scope:` header field.** Cheapest to parse, and consistent with the note header style that
  already carries `Status:`. Rejected by the vendored format checker: the header is positional, and
  adding a field means either editing the vendored script (D13 forbids a second implementation) or
  keeping the rule in the body, where it is prose again.
- **A persisted index file, regenerated and compared by a gate.** This was my second proposal. It
  removes hand-editing of the index, but it still creates one file every branch must touch, which is
  exactly the conflict the upstream rule names, and it needs a second checker to prove the file
  matches its sources. Printing the view has neither problem and no staleness window.
- **A hard gate on unclaimed units or missing `## Scope`.** Rejected: it would fail notes written by
  the upstream skill directly, which is the compatibility this design exists to keep.
